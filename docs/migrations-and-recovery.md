# Database migrations and backup/restore runbook

## Migration strategy

- `V1__initial_the database schema_schema.sql` is copied from the supplied the database schema initial migration.
- `V2__device_profiles.sql`, `V3__sync_performance.sql`, and `V4__master_admin_role.sql` preserve the supplied migration order.
- `V5__spring_runtime_compatibility.sql` adds Spring runtime columns/tables and numeric stock quantities.
- `V6__promotion_item_count_and_search_indexes.sql` adds promotion quantity constraints and query indexes.
- `V7__align_spring_runtime_schema.sql` aligns item/backups/settings columns with Spring entities.
- `V8__normalize_enum_columns_for_jpa.sql` safely converts native MySQL enum columns to `VARCHAR`, preserves existing values/defaults, and removes the now-unused enum types. Spring entities use `@Enumerated(EnumType.STRING)` consistently; no Hibernate-generated lowercase native-enum casts are required.
- The server profile uses `spring.jpa.hibernate.ddl-auto=none`; schema changes must be represented by Flyway.
- `spring.flyway.baseline-version=4` is only appropriate when onboarding a database already migrated to the current the database schema state. A database at an older revision must be upgraded and verified separately before Spring starts.

### Before touching an existing database

1. Stop both applications or put the POS into a maintenance window.
2. Create a MySQL backup with `mysqldump --format=custom --file=pre-spring-migration.dump "$DATABASE_URL"` (adapt credentials/URL syntax to your deployment).
3. Restore that dump into a disposable database and run the migration there first.
4. Compare `the database schema/schema.the database schema`, the migration history, the the current version SQL and every JPA entity. Do not assume Flyway baseline proves schema equivalence.
5. Confirm application login, 2FA, item listing, checkout, return, cancel, reports and restore on the clone.
6. Only then schedule a production maintenance window and retain the pre-migration dump until a recovery drill passes.

The migrations V1–V8 are MySQL-specific. The H2 desktop profile intentionally disables Flyway and relies on JPA schema creation/update. V8 is a forward-only schema change; do not edit previously applied migration files or manually delete the database to apply it.

## Encrypted backup format

- File suffix: `.posbak`; magic header `IPB1`.
- Snapshot JSON is gzip-compressed, then encrypted with AES/GCM/NoPadding using a 256-bit key derived from `BACKUP_ENCRYPTION_KEY` with SHA-256.
- A fresh 96-bit nonce is generated for every backup. The magic header is authenticated as GCM AAD, so altered data or a wrong key fails authentication.
- Business tables are allowlisted in code; table names are not read from user-controlled backup content. Auth sessions, token blacklist, audit/security/system logs and backup registry are intentionally not rolled back with business data.
- The snapshot includes the users table and therefore contains credential hashes and encrypted TOTP values; protect the encryption key and backup files as sensitive material. Never email or commit them to source control.

This uses a direct SHA-256 key derivation from an externally generated high-entropy secret, not a password-based scrypt KDF. Use a random secret generated by a cryptographically secure tool; do not use a memorable password.

## Create, preview, restore

1. Create a manual backup using `POST /api/backups` with a user authorized for `manage:settings`.
2. Confirm the encrypted file is present in `BACKUP_DIR` and not readable as plaintext. Keep an off-host copy of the encrypted file and the separately protected key.
3. Preview counts using `POST /api/backups/restore/{id}`. This verifies format, key and authenticated integrity; it does not mutate data.
4. To restore, call `POST /api/backups/restore` with JSON:

   ```json
   {
     "backupId": "<backup UUID>",
     "currentPassword": "<current user's password>",
     "confirmation": "RESTORE"
   }
   ```

5. Restore creates an automatic safety backup first and executes deletes/inserts within a transaction. Any database exception should roll back the data transaction. Preserve the safety backup and application logs until verification is complete.
6. Verify row counts, log in with a known authorized account, verify stock/loyalty and perform a controlled test sale/return on a non-production clone before resuming sales.

## Operational caveats

- Restore is a destructive business-data replacement. It does not restore login sessions, token blacklists, audit/security/system logs or the backup registry. Because user rows are replaced, database foreign-key cascades can remove login sessions, token-blacklist rows and security events; audit-log actor references may be nulled by the existing `ON DELETE SET NULL` constraint.
- A safety backup file can remain on disk if the database transaction later rolls back; the files endpoint helps find files not registered in the database.
- Run `./scripts/test-mysql.sh` from the project root after changing migrations. It starts/uses a local-only MySQL test container and runs Maven tests, including Flyway migration and JPA schema validation. Also verify dashboard and item reports, user-role reads/writes, promotion discounts, stock movement types, settings type round trips, backup create/preview/restore, and transaction rollback on a disposable database before production use. Do not point this test workflow at production or Supabase.
- Losing `BACKUP_ENCRYPTION_KEY` means the backup cannot be decrypted. Losing `TOTP_ENCRYPTION_KEY` means encrypted TOTP seeds cannot be decrypted. Store these keys separately in a secrets manager or offline recovery location.
